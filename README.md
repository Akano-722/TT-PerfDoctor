# TT-PerfDoctor

TauriTavern 的**性能诊断 + 可逆优化**扩展，iOS 优先。

它不替你「自动优化」，而是先量出卡在哪：主线程占用、帧率、点击延迟、消息 iframe 数、监听器泄漏、**谁在加监听/定时**、重消息分布，并用「空白遮罩 / iframe 隔离」把**绘制问题**和**计算问题**分开。所有优化开关都是你手动点、随时可关。

一句话流程：**先隔离方向 → 再逐个 A/B → 最后只改确认有收益的东西。**

---

## 为什么先做诊断

iOS 上没有控制台，凭感觉调优很容易调错方向。常见误判：

- 以为是「聊天记录太多」，实际是每条消息都挂了 HTML 前端 iframe。
- 以为是「角色卡太多」，实际是某个扩展每渲染一次就多注册一批监听器。
- 以为是「手机性能不行」，实际是一个小说排版扩展在反复重排整个聊天。
- 以为是「主线程被占满」，实际主线程只忙 20%，帧率却被绘制/视频解码压住。

这个插件把这几类信号分开显示，并用「录制 30 秒 + 泄漏对比 + 隔离探针」给出可复现的证据。

---

## 实战案例：iPhone 16 从 10 fps 到 30 fps

2026-10-24 的真实排查（iPhone 16 / iOS 18.7，无低电量模式）：

| 观察 | 数值 |
| --- | ---: |
| 正常聊天 | ~10 fps，手机持续发烫，按钮有延迟 |
| 空白遮罩（隐藏所有可见页面层） | 30.4 fps |
| 纯文本短对话 / MVU 长对话 | 7.6 / 10.7 fps |
| 禁用全部扩展 + 默认主题 | 流畅、不烫 |

排除过程：

1. 短对话和长对话都只有 8–11 fps，**聊天内容与 MVU 被排除**；
2. 主线程只忙 17–26%，且三个旧 A/B 全无变化，说明不是 JS 占满；
3. 空白遮罩 10 → 30 fps，说明有明显的绘制/合成开销，但页面全隐藏后仍有 30 fps 上限，另有持续负载；
4. 视觉扫描点名了全屏背景层和一个 0% 面积的播放中画中画视频；但背景/媒体相关开关、以及单独关闭保活脚本，帧率都没有变化，两个假设被排除；
5. 逐个启用扩展定位：元凶是一个**「小说阅读样式」扩展**，关闭后 ~10 → ~30 fps，按钮跟手、发热消失；
6. 归因里 `core/cssScope.js` 短时间内调度了 2936 次 `setTimeout`（疑似该扩展的样式作用域逻辑），属于典型的反复改样式/触发重排。

聊天内容、MVU、主题、iframe、保活视频等假设逐一被排除，最后才锁定到这一个扩展——这正是先做隔离探针、而不是直接堆优化的价值。剩下的 ~30 fps 与角色列表轻微加载延迟属于次级问题。

## 安装

扩展是纯前端模块，无构建步骤。

### 方式 A：Git 安装（iOS 推荐）

仓库：<https://github.com/Akano-722/TT-PerfDoctor>

1. TauriTavern → 扩展 → 安装扩展，填 `https://github.com/Akano-722/TT-PerfDoctor`（带 `.git` 也可以）。
2. 重载页面。
3. 在扩展管理里确认已启用。

> TT 只接受匿名 http(s) Git：不支持 SSH、URL 带账号密码、query/fragment、LFS、submodule、ZIP。

### 方式 B：本地目录

把整个 `TT-PerfDoctor` 文件夹放到数据目录任一位置：

- local（推荐）：`<data-root>/default-user/extensions/TT-PerfDoctor/`
- global：`<data-root>/extensions/third-party/TT-PerfDoctor/`

然后重启 / 重载，在扩展管理里确认已启用。

### 更新

扩展管理 → Perf Doctor → 更新（或删除后按原地址重装）→ 重载页面。当前版本见 `manifest.json`，历史见 [CHANGELOG.md](CHANGELOG.md)。

## 使用流程

1. 点左下角圆形「性能」按钮打开面板。
2. 先看「环境」：确认 ChatSurface 是否托管、JS-Slash-Runner 的渲染深度和流式开关。
3. 点「开始录制 30 秒」，然后**复现卡顿**：滚动消息、等 MVU 状态栏刷新、打开面板、切换聊天。
4. 录制结束后看「录制」区块的汇总。
5. 看「归因」：监听器、`setTimeout`/`setInterval` 按来源文件排序，找出持续在跑的那个扩展。
6. 用「定位探针」先分清方向：点「空白遮罩」——页面内容全隐藏后仍低帧率，问题就不在聊天或主题；若帧率明显回升，再查绘制/合成（详见下文）。
7. 用「实验 A/B」逐个开关，盯着帧率找因果。开关后至少等 2–3 秒再看。
8. 想查泄漏：先「记录基线」→ 来回滚动 / 切聊天 →「与基线对比」。
9. 「扫描聊天」找出字符数最大、带 iframe / script 的楼层。
10. 「复制 JSON 报告」，需要时贴出来分析。录制时插件会自动开启 TT 内置 HUD 并把它的长任务 / 事件循环 / invoke 数据写进报告。

面板关闭后采样自动停止，不常驻耗电。

## 指标怎么读

| 指标 | 含义 | 参考阈值 |
| --- | --- | --- |
| 帧率 | 每秒实际绘制帧数 | 滚动时 <45 说明明显掉帧 |
| 主线程占用 | 定时器被延迟的比例，近似「主线程有多忙」 | 持续 >30% 偏高，>60% 很卡 |
| 点击→下一帧 | 按下到界面有机会响应的延迟 | p95 >100ms 能明显感觉到 |
| 被阻塞峰值 | 单次最长主线程阻塞 | >200ms 会感觉「点了没反应」 |
| 消息 DOM | 当前实际挂载的 `.mes` 数 | 虚拟化开启时应远小于总楼数 |
| iframe | 页面里的 iframe 总数 | 持续 >30 就要查渲染深度 |
| 监听器净增 | 插件激活后 add/remove 的差值 | 滚动后只增不减 = 泄漏信号 |

注意：

- 监听器计数从**本插件激活时**开始，之前注册的不计入。
- 主线程占用是采样估算，不是精确 profiler，但足以区分 20% 和 80%。
- iOS 上拿不到可靠的 JS 堆内存，插件用 DOM 节点、iframe、监听器作为代理指标。

## 先看哪一项

| 症状 | 先做什么 |
| --- | --- |
| 所有界面都卡、手机发热，和聊天长度无关 | 「定位探针 → 空白遮罩」；仍然低就二分扩展（见实战案例） |
| 只有聊天卡，角色列表正常 | 看消息 DOM、iframe 数、JSR 渲染深度与流式开关 |
| 滚动才卡，停下来恢复 | CSS 性能模式；看 DOM 节点与图片 |
| 点击按钮有明显延迟 | 录制 30 秒，看峰值阻塞与归因 |
| 停止操作后仍是低帧率 | 空白遮罩 + 归因（常驻 interval / 高频 setTimeout） |
| 一进聊天就明显变差 | 对比空白聊天；查 MVU / JSR / 主题 |

## 定位探针（0.3 新增）

| 按钮 | 做法 | 怎么读 |
| --- | --- | --- |
| 空白遮罩 2.5s | 暂时隐藏 `#ttpd-root` 之外的所有页面层，测 2.5 秒 rAF | **明显回升**（例如 10 → 30）→ 可见内容在吃绘制/合成；**几乎不回升** → 瓶颈不在可见内容（查持续脚本、媒体解码、设备发热） |
| iframe 内 2s | 新建一个 1×1 同源 iframe，测它自己的 rAF | 和主页面一样低 → 宿主/合成器整体限速；比主页面明显高 → 主页面自身有重负载。注意主页面仍可见时结果会受其影响 |
| 扫描视觉嫌疑 | 列出大面积 fixed 层、`filter`/`backdrop-filter`、背景图、CSS 动画、canvas、video、iframe | 按「占屏百分比」排序，直接点名主题里最可疑的元素 |
| TT HUD 开关 | 调用 TT 自带 `__TAURITAVERN_PERF__` | 开启后左上角出现官方 HUD，可看长任务、事件循环延迟、invoke 次数 |

补充：

- 空白遮罩只影响**绘制**，不停止脚本、定时器、媒体解码；如果遮罩下仍然低帧率，说明不是「画得多」而是「有人在算」。
- 录制开始时会自动打开 TT HUD，结束后恢复原状态，并把 `snapshot()` 写进报告。部分 TT 版本未内置 HUD，会显示「当前版本未安装」，不影响其他探针。
- 「隐藏 iframe / canvas / video」只停止绘制：iframe 里的 JS 仍在跑，视频也仍在解码。要验证脚本开销用「彻底移除全部 iframe」，要停视频解码用「暂停视频/音频」。
- 探针结果会显示在面板并写入报告的 `probe` / `visual` 字段。

## 归因（0.2 新增）

录制开始时清零，把这几类调用按**来源脚本**聚合：

- `addEventListener`：谁在加监听。渲染消息时几百条属正常；停止操作后还一直涨才是泄漏。
- `setTimeout`：谁在反复排队任务。持续高位的文件就是"主线程一直忙"的嫌疑人。
- `setInterval`：同时显示**仍然存活**的 interval 数量和最久存活时长。只建不清的，一眼看出来。

来源取调用栈里的文件和行号，例如 `third-party/SomeExt/index.js:412`。实现上每次只解析一次调用栈、按回调函数缓存，并有每秒 400 次的采样上限，不会自己把页面拖慢。

注意：

- 只统计**主文档**。iframe 内部（MVU 状态栏自己的脚本）是独立 JS 世界，这里看不到——用「实验 A/B」的「彻底移除全部 iframe」来测它们的脚本开销。
- 匿名回调、`eval` 出来的代码可能显示 `(其他)` 或没有来源。
- 录制结束后结果保留，方便慢慢看；点「清空数据」或下次录制时清零。

## 实验 A/B（0.2 新增，0.3 扩充）

除「彻底移除 iframe」外，所有开关**只在本次页面生效，刷新即恢复**，不留设置。开关后等 2–3 秒再读帧率。

| 开关 | 作用 | 若帧率明显回升说明 |
| --- | --- | --- |
| 禁用动画 / 过渡 | 全局 `animation/transition: none` | CSS 主题动效在吃合成 |
| 暂停运行中的动画 | 暂停 `document.getAnimations()` + `animation-play-state: paused` | JS 创建的动画 / 过渡在持续重绘 |
| 关闭滤镜 / 模糊 / 阴影 | 对大图层/特效候选元素内联置空 `filter` / `backdrop-filter` / `box-shadow` | 大面积的模糊或阴影是 GPU 大头（iOS 上很常见） |
| 移除整页背景图 | 对全屏层/主题元素内联置空 `background-image` | 大图/多层背景在反复解码或合成 |
| 隐藏 canvas / video | `canvas`、`video` 不显示（不停播放） | 特效层或视频的**绘制**在吃 GPU |
| 暂停视频 / 音频 | 对正在播放的 `video`/`audio` 调用 `pause()` | 画中画、背景视频、音乐可视化在持续解码 |
| 隐藏聊天内 iframe | `#chat iframe { display: none }` | MVU / HTML 状态栏的**绘制**是开销 |
| 隐藏聊天外 iframe | 隐藏聊天区之外的 iframe | 常驻组件的**绘制**是开销 |
| 彻底移除全部 iframe | 从 DOM 删除所有 iframe | iframe 里的**脚本**也在吃 CPU（隐藏不会停脚本） |

帧率不动不一定是开关无效：如果「空白遮罩」也是同样低帧率，瓶颈就在页面之外，A/B 自然没反应。

样式类开关（去滤镜、去背景图、隐藏 iframe/media、暂停动画）会用**内联 `!important`** 覆盖主题规则，因为主题常用 `#bg1 { ... !important }` 这类高优先级选择器，普通 `*` 规则压不过它。代价是只作用于开关那一刻已存在的节点；主题若重建节点，需要重新勾选一次。

> 部分主题会在每次渲染时重新创建动画/特效，必要时多切几次再观察。

## 优化开关

### CSS 性能模式（可逆）

- 给非最后一条消息加 `content-visibility: auto`，跳过屏幕外消息的布局/绘制。
- 给页面上的 `<img>`（包括角色卡头像/封面）补 `loading="lazy"` / `decoding="async"`，可减轻角色列表滑动时的加载延迟。
- 不改数据、不改其他扩展。
- 需要 WebView 支持 `content-visibility`（Safari 18+）。不支持时该条自动无效，不会报错。
- 如果滚动位置出现跳动或消息高度异常，立刻关掉。

### JSR 渲染深度（需重载）

设置 `extensionSettings.tavern_helper.render.depth`。>0 时只渲染最近 N 楼的 HTML / MVU 前端。面板提供 1 / 3 / 5 / 10 / 20 五档；`1` 只保留最后一条的前端，适合极限排查，日常建议 3–10。

- 只影响「渲染」，不影响聊天记录和模型上下文。
- 往上翻旧楼时文本仍在，但旧楼层的前端不会重建。
- 会先弹确认框，再写入设置。

### 关闭流式渲染（需重载）

设置 `render.allow_streaming = false`。生成过程中不再反复重绘，完成后再渲染一次。

- 虚拟化模式下本来也不支持流式渲染。
- 会影响你看到回复的过程体验，自行取舍。

### 虚拟化

插件**不代替你改**这个开关。原因：TT 在页面启动时读取 `chat_virtualization_enabled`，本页生命周期内改变会直接报错，必须重载；而且它属于宿主设置，不是扩展设置。

面板会在「建议」里告诉你当前是否托管。未托管时：TauriTavern 设置 → 性能 → 打开「聊天 DOM 虚拟化」→ 重载。

## 隐私

- 所有测量数据只在本机内存中，**不上传**、不写聊天记录、不修改设置（除非你点确认后写入 JSR 深度/流式开关）。
- 面板关闭即停止采样；录制数据在「清空」或下次录制时重置。
- A/B 开关只影响当前页面，刷新即恢复（「彻底移除 iframe」需要刷新恢复）。

## 已知限制

- 「彻底移除 iframe」会停掉其脚本，但不可在页面内恢复，只能刷新。
- 空白遮罩只停止绘制，不暂停脚本、定时器和 worker；它回答的是「画得动吗」，不是「谁在算」。
- 样式类 A/B 只作用于启用那一刻已经存在的节点；主题/扩展重建节点后需要重新勾选。
- 部分 TT 版本没有内置 `__TAURITAVERN_PERF__`，TT HUD 显示不可用属于正常现象。
- 归因只覆盖主文档：iframe 内部的监听器 / 定时器不可见；每秒最多采样 400 次调用栈，高频调用会标注丢弃数量。报告里的 `debugStacks` 只在完全解析不出来源时保留最多 3 条原始栈，便于排查。
- 不替换 JS-Slash-Runner / LittleWhiteBox 的渲染器，也不参与 ChatSurface participant。
- 不修改聊天数据、不删除历史、不上传任何内容。
- 在原生 SillyTavern 中加载时，TT 专属指标会显示为不可用。

## 开发

- 无构建、无依赖，ESM 直接加载。
- `metrics.js` 只放浏览器标准探针；`ui.js` 只放面板；`index.js` 负责激活、动作与报告。
- 调试句柄：`window.__TT_PERFDOCTOR__.getReport()` / `.getState()` / `.scanChat()`。
- 兼容上游 SillyTavern 不会被破坏；TT 专属部分全部做了特性检测。

## 路线

1. **已完成**：诊断 + 可逆优化；真机定位出小说阅读扩展（~10 → ~30 fps）。
2. **可选下一步**：角色卡列表懒渲染（`content-visibility` + 图片解码），减少滑动加载延迟。
3. **可选**：如需保留小说排版扩展，针对其 JS/样式做性能模式或向作者提交补丁。
4. **之后再谈**：旧聊天归档与云端异步索引——需要独立的数据迁移设计，不在本插件里顺手做。
